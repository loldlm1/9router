## Overview

Prevent avoidable interruptions of long Codex tasks through 9router, preserve
Responses API stream integrity, and make unavoidable connection failures
diagnosable and recoverable by the client. Preserve the selected
`cx/gpt-6-astra` model and reasoning settings.

The screenshots establish an interrupted connection and a Codex reconnect
attempt. Static source review identifies several defects and reliability gaps
that can amplify this class of incident. It does not establish which component
closed the connection on the VPS. Implementation should correct those defects,
test the actual transport boundaries, and validate the result on the VPS before
claiming the reported incident is resolved.

The initial planning turn inspected source, test definitions, and official
documentation and created only this plan. The subsequently authorized sprint
batch used synthetic tests and isolated data. It did not search local incident
logs, inspect personal Codex sessions or real provider data, or connect to the VPS.
The user will pull, rebuild, and start 9router on the VPS manually; operational
acceptance remains separate from the completed local implementation batch.

### F1 - P1: Codex preflight can withhold a healthy stream indefinitely

**Evidence**: `open-sse/executors/codex.js:25`,
`open-sse/executors/codex.js:428`, `open-sse/executors/codex.js:469`,
`open-sse/executors/base.js:150`,
`open-sse/handlers/chatCore/streamingHandler.js:88`.

`_peekSseTransientError()` buffers the response until it sees selected text or
function-argument events, reaches its nominal 256 KiB threshold, sees a matching
error string, or reaches EOF. There is no time bound on `reader.read()` or the
whole peek. Creation, progress, reasoning, comments, and other tool event types
do not end this preflight. The connect timer has already been cleared, while
the streaming watchdog and downstream response have not yet been created.

**Impact**: During a long reasoning response, Codex and any ingress proxy can
receive nothing even while upstream events arrive. A stalled prelude can retain
an active request without the router's intended stream timeout. The nominal
byte limit is measured as JavaScript string length, and matching raw substrings
does not distinguish error events from ordinary model content.

**Confidence**: Confirmed source defect; contribution to this VPS incident is
unconfirmed. Address in Sprint 3, measure in Sprint 1.

### F2 - P1: Client cancellation does not reach upstream dispatch during startup

**Evidence**: `src/sse/handlers/chat.js:243`,
`src/sse/handlers/chat.js:289`, `src/sse/handlers/chat.js:338`,
`open-sse/handlers/chatCore.js:78`, `open-sse/handlers/chatCore.js:333`,
`open-sse/executors/base.js:123`, `open-sse/executors/codex.js:453`.

The inbound request signal is passed to account admission, but is not passed to
`handleChatCore()` and its new stream controller. Response cancellation is bound
only after dispatch and the SSE peek finish. Retry waits are ordinary timers
without cancellation support.

**Impact**: A disconnected client can leave the old request fetching, peeking,
or waiting to retry while Codex starts another attempt. This can occupy account
leases, spend upstream work, and delay subsequent agent requests. The existing
response lifecycle wrapper releases leases after body settlement, but does not
cover this startup cancellation gap.

**Confidence**: Confirmed source defect. Address in Sprint 3; verify admission
cleanup again in Sprint 5.

### F3 - P1: Responses termination is inconsistent across response paths

**Evidence**: `open-sse/handlers/chatCore/streamingHandler.js:26`,
`open-sse/utils/stream.js:255`, `open-sse/utils/stream.js:384`,
`open-sse/utils/stream.js:464`, `open-sse/utils/streamHandler.js:102`,
`open-sse/utils/streamHandler.js:125`,
`open-sse/utils/responsesStreamHelpers.js:6`.

The same-format translation path tracks a Responses terminal and synthesizes a
failure on premature EOF. The generic passthrough path selected for matching
Codex/Droid user agents appends `[DONE]` and finalizes on EOF without the same
terminal requirement. The outer disconnect wrapper has its own terminal flag
that tracks only its synthesized payload: it cannot tell whether the inner
stream already delivered `response.completed`. A later socket error can
therefore append a contradictory `response.failed` for a client still reading.

The terminal helper also omits the documented `response.incomplete` event and
`incomplete` status. Its generated failure invents a new response ID even after
`response.created` supplied one. Line-based parsing and the separate flush
implementation need explicit framing tests, especially for partial events.

**Impact**: Equivalent Responses requests can report different outcomes by user
agent; truncated output can be accounted as successful; valid terminal outcomes
can be followed by another failure. These defects complicate client recovery.
Do not assume the invented ID is the cause of the screenshot's reconnect: the
client clearly surfaced the generated error message.

**Confidence**: Confirmed source defects; the post-terminal race needs a
controlled streaming test. Address in Sprint 2.

### F4 - P2: Current success records and error logs obscure the failure phase

**Evidence**: `open-sse/handlers/chatCore.js:521`,
`open-sse/handlers/chatCore/streamingHandler.js:47`,
`open-sse/handlers/chatCore/streamingHandler.js:99`,
`open-sse/handlers/chatCore/streamingHandler.js:133`,
`open-sse/utils/stream.js:82`, `open-sse/utils/streamHandler.js:82`.

The routing log records the HTTP status before streaming. Request details are
initially saved as successful, and `finalizeStream()` invokes a success-oriented
callback for failure terminals and premature EOF as well as completed responses.
Socket logging prints the outer message and stack without a bounded classification
of `error.cause.code`, stream phase, or last activity. A session color/tag is not
a unique identifier for overlapping attempts.

**Impact**: HTTP 200 can conceal a failed stream, and the reported `terminated`
does not distinguish a socket reset from a body timeout or router cancellation.
This prevents reliable diagnosis and before/after measurement.

**Confidence**: Confirmed source defects. Address diagnostics in Sprint 1 and
outcome accounting in Sprint 2.

### F5 - P2: The Responses route lacks a complete downstream liveness policy

**Evidence**: `open-sse/utils/sseConstants.js:18`,
`open-sse/handlers/chatCore/streamingHandler.js:106`,
`open-sse/utils/stream.js:243`, `open-sse/utils/streamHandler.js:192`.

The client-facing SSE header set omits `X-Accel-Buffering: no`, although a
different header variant defines it. There is no scheduled heartbeat in the
Codex streaming route. The same-format translation branch ignores upstream
comment-only lines, whereas generic passthrough forwards them.

**Impact**: A buffering or idle-limited ingress can delay or close a quiet stream.
This exposure depends on VPS topology and configuration, which are unknown.
SSE comments can keep a transport active, but do not repair a closed upstream
socket and must not be assumed to reset Codex's semantic event idle timer.

**Confidence**: Confirmed missing safeguards; an ingress-related incident cause
is a hypothesis. Address in Sprint 4 and verify the public path in Sprint 5.

### F6 - P2: Router, HTTP-client, and Codex timeout budgets are independent

**Evidence**: `open-sse/config/runtimeConfig.js:53`,
`open-sse/config/runtimeConfig.js:56`,
`open-sse/utils/proxyFetch.js:229`, `open-sse/utils/proxyFetch.js:306`,
`open-sse/utils/proxyFetch.js:353`.

The router defaults to a 360-second inter-read stall budget. Direct and relay
requests use captured global fetch, and proxy dispatchers have no explicit
streaming timeout policy. Undici documents a 300-second body inactivity default;
current Codex documentation separately lists a 300000ms SSE idle default.
`STREAM_FIRST_CHUNK_TIMEOUT_MS` is not wired into the Codex preflight; its other
consumer is a Kiro path, so changing it is not a demonstrated Codex fix.

**Impact**: Raising one router setting may leave a shorter timeout active in
another layer. The deployed Node version determines the bundled Undici used by
native fetch; the repository's npm Undici version alone does not establish it.

**Confidence**: Confirmed policy gap, not a confirmed timeout diagnosis. Verify
actual dispatcher behavior in Sprint 4 and effective VPS/client settings in
Sprint 5. Do not present Node `requestTimeout` or `keepAliveTimeout` as active
response-stream duration limits.

## Scope And Fixed Decisions

- **In scope**: Codex HTTP Responses SSE startup, terminal integrity, downstream
  cancellation, existing retry boundaries, scoped timeout and heartbeat policy,
  accurate outcomes, deterministic fault tests, and a VPS validation/rollback
  runbook.
- **Non-goals**: Changing Astra models or reasoning levels; replacing Codex's
  agent loop; making every upstream outage invisible; automatic replay after
  streamed output; durable event storage; background-mode or WebSocket migration;
  account strategy redesign; unrelated translator, dashboard, database, or
  deployment-platform refactors.
- **Protocol**: Never generate `response.completed` for missing or partial
  output. Preserve upstream IDs, sequence numbers, event order, tool-call IDs,
  arguments, reasoning metadata, and genuine terminal reasons. Recognize
  completed, failed, and incomplete outcomes; retain existing `response.done`
  compatibility without treating every such event as success.
- **Retry ownership**: The router may use its existing bounded retries only
  before it commits a downstream response and within a documented safe rejection
  policy. Once headers/events are committed, preserve one attempt and let Codex
  own request recovery. Never concatenate two generations or replay a partly
  delivered tool call. A retry of a POST can repeat upstream work even before
  visible output; lack of output alone is not proof that replay is safe.
- **Persistence**: Keep the existing foreground ChatGPT backend route and
  `store=false` behavior. Public OpenAI background-response retrieval and cursor
  resume are not evidence that this internal backend supports resumable streams.
- **Compatibility**: Select Responses integrity behavior by wire format, not
  user-agent spelling. Keep compact/non-streaming and other provider contracts
  stable, with relevant regression coverage.
- **Implementation size**: Reuse the existing stream controller, response
  lifecycle wrapper, format helpers, Vitest, Node streams, and installed Undici.
  Introduce no new runtime dependency or global fetch policy for all providers.
  Put new policy constants under `open-sse/config/` as its `AGENTS.md` requires.
- **Operational scope**: Preserve the deployment method actually in use. The
  repository supports a standalone VPS runner and Docker; no Kamal, proxy/CDN,
  systemd, or PM2 installation is inferred or introduced by this plan.

## Implementation Contract

### Lifecycle and protocol

Use one per-attempt lifecycle context shared by the Responses transform and the
disconnect wrapper. Distinguish request cancellation, upstream transport error,
router inactivity timeout, normal EOF, and protocol terminal status. Preserve the
first observed response ID, last upstream sequence number, and terminal reason.
Keep upstream terminal parsing distinct from enqueueing a complete terminal frame
to the final downstream readable: an upstream event still buffered when the
stream errors must not be reported as delivered. Enqueueing is not proof of
receipt by the remote client; validate delivery at the client in Sprint 5.

On clean EOF without a valid Responses terminal, report failure. On transport
failure before a delivered terminal, emit at most one well-framed failure when
the downstream remains writable. Reuse the known response identity; before a
response identity exists, use a documented compatible error envelope instead of
inventing an unrelated completed response. Preserve real failed/incomplete
terminals without replacing their reasons. After a terminal was delivered, do not
append a contradictory terminal because the socket later closes. `[DONE]` alone
is not Responses completion; preserve any required legacy sentinel compatibility
without duplicate sentinels or using it to hide truncation.

Pair all listeners, readers, timers, upstream cancellation, pending counts, and
account lease release with idempotent cleanup. Cancellation must remain effective
before headers, during preflight/retry wait, and throughout streaming. Do not
write failure bytes to an already cancelled client.

### Initial policy choices to implement and then validate

| Control | Proposed behavior |
| --- | --- |
| Codex preflight | Introduce `CODEX_SSE_PEEK_TIMEOUT_MS`, default 1000ms, with validated finite bounds in config. End on a complete normal Responses event or the deadline/byte cap, without waiting for visible text. Hand the existing reader and buffered bytes to the live stream without losing a pending read |
| Prefix size | Move the existing peek cap into Codex config and count actual bytes. Reaching the cap ends peeking; it must not truncate the response or require buffering a huge terminal event before forwarding |
| Router idle | Introduce an optional Codex-specific idle override, `CODEX_STREAM_STALL_TIMEOUT_MS`, falling back to existing `STREAM_STALL_TIMEOUT_MS`. Preserve the current default pending measurement; do not raise all providers' budgets |
| Outbound HTTP client | Use a reused Codex-scoped dispatcher policy whose finite body inactivity timeout is greater than the router idle budget by a documented cleanup margin. Verify the setting actually affects captured/native fetch and proxied paths. Keep connect/header timing separate |
| Downstream heartbeat | Introduce `CODEX_STREAM_HEARTBEAT_MS`, initially 15000ms, with explicit zero-to-disable semantics. Emit SSE comments between complete frames while waiting, respect backpressure, and stop on every terminal/cancel/error path |
| Client-facing headers | Add buffering protection and `no-transform` for the affected SSE response; verify the actual ingress honors it and route aliases preserve it |
| Codex client configuration | Measure the affected provider's effective idle setting against permitted event gaps and router termination budget. Document a finite per-provider override only if necessary; do not silently edit the user's config or increase retry counts as a substitute for fixing failures |

Heartbeats are downstream transport activity, not upstream model progress. They
must never reset the upstream inactivity watchdog, mutate model output, or add
fake reasoning/tool events. A slow consumer can stop upstream reads through
backpressure; do not label that as proven upstream network silence. Record the
observable boundary accurately and exercise backpressure in tests.

### Task 2.1: Share terminal state across formatting and disconnect handling

- **Location**: Responses helpers, stream transform/controller, streaming handler.

## Release And Rollback Procedure

This procedure is the operator handoff. The user performs VPS pull/rebuild/start;
the local commit batch does not execute these operations. Live verification
follows manual startup. Preserve the current working artifact before switching.

1. Prepare the candidate and capture the exact known-good release identity,
   supervisor command, provider settings, environment variable names/values in
   private operator storage, and ingress config backup. Do not print secrets or
   commit that storage. Record database/volume ownership; no restore is required
   for this code-only change.
2. Pull the five locally validated sprint commits with `git pull --ff-only origin master`
   in the intended VPS checkout and record the revision. The user rebuilds and
   starts the candidate using the existing deployment method. Record its artifact
   identity and drain active Responses requests before replacing the serving
   process. Prefer an isolated canary before replacing the serving release.
   For the standalone runner, prepare a separate release/build directory;
   `npm run vps -- --rebuild` is not
   a safe command to run blindly over the serving release.
3. After manual startup, validate the candidate through both origin and public
   ingress and the affected Codex build using Tasks 5.2 and 5.3. Record the source
   tree/build digest that was actually tested. Do not rebuild a different artifact
   and assume it is equivalent. If using a separate canary, the user promotes
   that validated artifact with the existing deployment method after draining
   active streams. Do not claim the incident resolved before the live checks.
4. After promotion, verify `/api/health`, one actual Responses completion, one
   cancellation/reuse flow, and the absence of leftover active/queued work.
   Observe at least the same 30-minute window used for canary. Compare first-event
   delay, transport failures by cause, missing-terminal failures, reconnects,
   and lease cleanup against the recorded workload/sample sizes.
5. Roll back immediately for fabricated/duplicate terminal outcomes, corrupted
   tool payloads, leaked leases, growing retry loops, or a clear regression of
   stream delivery. Restore the prior release artifact plus prior timeout,
   heartbeat, provider, and ingress configuration using the worksheet commands.
   Drain first when possible. Verify health and a completed stream after switchback.
   Do not delete data volumes, reset the repository, or rewind Codex task history.
6. For source rollback, revert dependent sprint commits in reverse order
   (`S5`, `S4`, `S3`, `S2`, `S1`) as required, preserving user changes. Do not mix
   incompatible stream-controller/transform versions. Operational rollback can
   restore the previous artifact immediately; it need not wait for source reverts.

## Execution Order And Handoff

Execution used the planner's active-plan state and updated validation, commit,
and sprint transitions in order. On continuation, inspect that state before
making changes; do not initialize a second execution or repeat completed sprints.
Mark local implementation complete after the Sprint 5 commit while retaining
the separate operational checklist above for the user-owned VPS handoff.

For **every** sprint: complete its tasks, run and record its validation, document
residual risks, create **exactly one sprint-specific commit**, and record the
rollback point **before** starting the next sprint. If validation uncovers a
defect, fix it within the active sprint and rerun the affected checks before its
single commit. Do not amend or rewrite previous commits unless separately
authorized. An unresolved operational prerequisite remains explicit and does not
become a passing check merely because code/tests are complete.

Dependency order is `Sprint 1 -> Sprint 2 -> Sprint 3 -> Sprint 4 -> Sprint 5`,
followed by the user-operated rollout and live observation procedure. No later sprint
starts speculatively. Within a sprint, fixture/diagnostic documentation can run
independently of code once the contract is fixed, and independent test commands
can run together only with isolated state. Shared stream/executor edits are
sequential. This is a dependency map, not authorization to spawn sub-agents.
